# 存储、备份与数据安全规范

修改存储、缓存、归档、备份、删除、文件替换或跨端传输前必须阅读本文件。通用开发、测试、提交和安全规则仍以仓库根目录 `AGENTS.md` 为准。

## 存储与缓存不变量

- 设置页以录像或备份容量上限呈现，不会预占或保证磁盘空间；配置层仍以系统和其他应用所需的最低空闲空间保存，`StorageSpacePolicy` 是最小预留规则的唯一来源。
- NAS/网络备份位置属于滚动归档存储。空间检查只读取真实卷空间，不做文件探测；低于预留值时，按最旧优先循环清理已确认归档的副本（`Verified` 和已成功归档的 `LocalDeleted`）。
- NAS 单轮最多处理 200 条、同根互斥，每删除一条都回读真实空间。本地循环不依赖 NAS 可达性；远端确认超过 24 小时后，`Verified` 本地副本仍可按容量策略清理并记录未确认原因码。
- 对账只把“明确不存在”视为丢失；`Unavailable` 不改变归档状态。
- “是否待备份”统一通过 `ArchiveBackupStatePolicy` 判定：
  - `LocalMissingUnverified` 与 `BackupLost` 计入待备份，且不自动恢复。
  - `LocalDeleted + CapacityCleanupUnconfirmedRemote` 计入待备份，直到对账确认。
  - `LocalDeleted + ManualCleanup` 不计入待备份，也不能作为 NAS 存在证据。
  - RemainingCount 为 0 时必须区分“已清理/无待备份”与“已同步”。
- Web 转码缓存、剪辑预览和剪辑下载等可重建产物存入 `%LOCALAPPDATA%\ExpressPackingMonitoring\cache`，并受 Web 缓存上限清理。
- 设备凭据、根密钥、订单接收方、电脑昵称和备份上传状态等持久状态统一放在 `mobile-backup-state`，绝不能放入 cache。
- Web 视频操作使用“剪辑”或“剪辑并下载”，不得称为“导出视频”，避免与原片下载混淆。

## 删除与文件替换安全

- 录像、数据库、配置、更新负载和生成输出的删除都按并发敏感操作处理。删除前必须在与创建或替换相同的同步范围内确认文件所有者、生命周期和源/目标关系。
- 失败任务不能仅因目标存在就删除目标；目标可能由另一个并发任务成功发布，或源文件可能已被其他任务移动、替换。
- 不完整输出的清理必须位于其创建操作和锁内。只有原始源仍安全保留，且当前操作能证明目标由自己创建时，才允许删除。
- 自动删除重要数据时记录原因和精确目标；可行时优先使用可恢复清理或明确的数据库删除记录。
- 每项删除或替换修复都要增加竞态回归测试：任务 A 成功发布目标后，任务 B 才进入失败清理，测试必须证明 B 不会删除 A 的有效结果。

## 跨设备备份兼容性

- 设备注册、备份鉴权、上传和确认回执的变更都视为双端协议变更。主机和客户端必须显式交换协议、注册、鉴权、应用版本、构建版本和能力，不得只根据显示版本猜测兼容性。
- 不兼容客户端必须在显示主机审批、签发/轮换/保存令牌之前被拒绝，并返回结构化升级信息：需要升级哪一端、最低兼容版本和可信下载地址。
- 手机或录制工位必须在请求令牌前拒绝不兼容主机。兼容失败可以阻断连接和备份，但绝不能删除或重置本地录像、数据库、上传队列、稳定设备 ID 或最近主机提示。
- 最低版本和协议号只放在集中兼容策略代码中，不在规范文档写死。调整策略或线协议时同步更新桌面端与移动端回归测试。
- 提高主机最低客户端版本前，先发布兼容客户端；发布前验证两个升级方向及更新但仍兼容的对端。

## 历史录像业务类型筛选

`GET /api/mobile-backup/videos` 新增可选 `mode=shipping|return`，省略或空值表示全部。非法值返回 HTTP 400 与 `invalid_recording_mode`。服务端在分页和统计前筛选，`total` 和 `deviceTotal` 使用同一业务类型及关键字条件；响应回显规范化的 `mode`。

手机在筛选请求中检查回显；旧电脑未回显时不把未筛选列表当成筛选结果，保留本地筛选并提示升级电脑端。该扩展不改变协议版本、鉴权或上传回执，不清理本地录像及设置。

## 心跳响应回传电脑名

`POST /api/connections/heartbeat` 的 200 响应新增 `computerName`，与注册响应的 `computerName` 同源（主机节点名，不是机器名）。手机端每次心跳后按它纠正"已连接电脑"显示名，主机改名后不必重新配对；字段缺失或为空时保留本地已存的名字，禁止用它清空。

该字段只影响展示名，不改变协议版本、鉴权、心跳间隔或"检查是否还是备份主机"的判定，旧客户端忽略即可。

## 设备身份与昵称

- 设备身份只有设备号（`VideoRecords.SourceDeviceId`）：筛选、列表、导出、归档目录一律按设备号命中；昵称只是显示属性，用户随时可以改
- 设备录像目录名**就是完整设备号**（见 `Services/RecordingDeviceFolderNaming.cs`）。这条是硬约束：目录名必须是设备号的**纯函数**——同一个设备号永远同一个目录、不同设备号永远不同目录，不依赖任何需要持久化的分配状态
- 不要引入"主机分配的序号"之类更好看的方案。序号要靠一份额外的映射表存着，那份表丢失或损坏时所有设备都会重新编号，同一台设备的录像散进两个目录；分配、回收、落盘失败、以及昵称表自身的保留期与条数上限，每一处都是分裂风险。目录名难看由录像根目录下的快捷方式解决
- 也不要截短设备号。截短会撞号，撞上就是两台设备的录像混进同一个目录，比目录名难看严重得多。设备号含非法字符或超长而必须处理时，要补设备号哈希后缀，保证"不同设备号 → 不同目录"在任何输入下都成立
- 目录与昵称的对应关系由录像目录里的快捷方式给出（`Services/RecordingDeviceFolderShortcuts.cs`）：快捷方式建在分类目录里（`手机备份\安卓1.lnk` -> `手机备份\<设备号>`），只为磁盘上真实存在的设备目录建，改名后清掉旧链接。清理时只删确认指向本分类目录下设备目录的 `.lnk`，用户自己放进来的文件一律不碰；外壳组件不可用时只记一次日志，绝不影响录像与备份。早先的 `设备对照表.txt` 已由它取代并会被自动清掉
- 两代老目录（`设备-<后六位>`、更早的 `<昵称>-<后六位>`）由 `Services/RecordingDeviceFolderMigrator.cs` 在启动时迁移，覆盖本地录像根与所有备份位置。约束：匹配方向是"从数据库的完整设备号算出后六位再去磁盘找"，两台设备后六位撞上时两边都跳过并告警（绝不猜归属）；只移动不复制不删除，目标已存在时按日期子目录合并且同名文件一律跳过；数据库回写带乐观条件，且只在文件确实已经在新位置时才改，不制造悬空路径
- 迁移必须可重复执行并自愈：搬完目录还没回写数据库就断电时，下一轮按"库里还是老路径、文件已在新位置"把数据库补上，因此不需要额外的迁移日志文件。NAS 不可达只跳过归档那一侧，本地照常迁移，下次启动再补；文件被占用同样是跳过而非失败
- 昵称只保存"最新一份映射"，不逐条写进录像记录：手机登记表 `mobile-backup-state\order-receivers.json`（设备号、昵称、平台、最后出现时间）与电脑昵称表 `computer-nicknames.json`。新写入的录像记录不再带昵称；历史记录里的 `SourceDeviceName` 是老库遗留值，只在主机完全不认识这台设备时兜底
- 设备只要在这台主机上留下过录像就长期保留，不按 30 天活跃期清理：映射是录像来源名的唯一来源，清掉它老录像就只剩设备号了。保留期只作用于"没有录像、也不是用户改名"的设备；条数上限 512，超限时先清这一类
- 主机启动时用库里已有的录像来源补齐映射（每台设备取最近一条记录里的名字，同名时最近还有录像的设备优先，另一台带上设备号后缀区分），老库升级后老录像即可显示同一个当前名字，设备不用等上线
- 命名只用"设备号 + 平台前缀"：平台未知（旧版 App 上报没带平台信息）时沿用这台设备已有的自动名前缀，不按"从机"兜底改名；没有设备号的匿名上报（未配对手机探测主机能力等）不登记设备，避免凭空多出"从机"
- 补齐时顺带修回被兜底命名改坏的名字：设备录像里用过"手机N/安卓N/苹果N/电脑N"而当前是"从机N"时改回那个名字，用户手改过的名字不动
- 上传落库用主机分配的昵称：电脑工位先经电脑昵称表分配，结果原样交给手机登记表（`trustProvidedName`），避免两张表各编一套"电脑N"；客户端自报的名字只在主机完全不认识这台设备时使用
