# 存储、备份与数据安全规范

修改存储、缓存、归档、备份、删除、文件替换或跨端传输前必须阅读本文件。通用开发、测试、提交和安全规则仍以仓库根目录 `AGENTS.md` 为准。

## 存储与缓存不变量

- 预留空间是给**整块磁盘**留的安全空间（整个磁盘共享，其他软件占用也算在内），不是"本软件最多占用多少"。设置页不露出这个参数：加载配置时清掉历史"容量上限"反推出来的预留值一次，其余默认值只由 `StorageSpacePolicy` 按磁盘类型给；只有用户对某块磁盘右键"设置预留空间…"才写回配置。
- 预留值不预占、也不保证磁盘空间，只在写录像/备份前作为可用性判断依据。
- NAS/网络备份位置属于滚动归档存储。空间检查只读取真实卷空间，不做文件探测；低于预留值时，按最旧优先循环清理已确认归档的副本（`Verified` 和已成功归档的 `LocalDeleted`）。
- NAS 单轮最多处理 200 条、同根互斥，每删除一条都回读真实空间。本地循环不依赖 NAS 可达性；远端确认超过 24 小时后，`Verified` 本地副本仍可按容量策略清理并记录未确认原因码。
- 对账只把“明确不存在”视为丢失；`Unavailable` 不改变归档状态。
- “是否待备份”统一通过 `ArchiveBackupStatePolicy` 判定：
  - `LocalMissingUnverified` 与 `BackupLost` 计入待备份，且不自动恢复。
  - `LocalDeleted + CapacityCleanupUnconfirmedRemote` 计入待备份，直到对账确认。
  - `LocalDeleted + ManualCleanup` 不计入待备份，也不能作为 NAS 存在证据。
  - RemainingCount 为 0 时必须区分“已清理/无待备份”与“已同步”。
- Web 转码缓存、剪辑预览和剪辑下载等可重建产物存入 `%LOCALAPPDATA%\ExpressPackingMonitoring\cache`，并受 Web 缓存上限清理。
- 设备凭据、根密钥、订单接收方、电脑昵称和备份上传状态等持久状态统一放在 `mobile-backup-state`，绝不能放入 cache。
- 备份上传的分片暂存在**该上传任务选中的录像存储卷**内的 `.packingproof-staging` 目录，与最终录像同卷：既不占用系统盘，也让完成落盘成为同卷改名。同一录像一旦选定卷，断点续传、完成落盘和重启恢复都只能继续原卷；磁盘未接回时按 `storage_unavailable` 拒收，不能为了负载均衡搬迁半成品或改写到别的磁盘。
- 保存主机接收新录像时通过 `StorageLocationResolver` 获取全部可写本地根目录，再按物理磁盘负载、剩余空间、预留空间和待接收字节选卷。Windows 必须通过卷的物理磁盘 extent 归一化：同一块物理磁盘上的 `C:\`、`D:\` 等多个盘符共享一个写入预算，不能当成分开的磁盘来增加并发；物理盘识别失败时也保守地归入同一个未知物理盘预算，不能把多个盘符误当成多块盘。macOS / Linux 无法取得物理盘 identity 时按挂载点分组。录像任务开始后不再换盘。
- 主机并发不能使用“HDD=1、SSD=2”这样的固定最终上限。初值只用于安全起步，随后必须依据真实上传分片的累计写入量、实际耗时和排队情况动态调整：吞吐仍上升时可继续增加，达到平台期时停止增加，出现明显回退、写入延迟翻倍或排队积压时快速降低。判断依据必须是真实上传写入和刷盘结果，不得另跑合成 benchmark；目标是贴近实测上限并保留少量余量。
- `host_storage_busy` 表示某个目标盘暂时没有写入余量，客户端按任务退避并继续尝试其他可调度任务，不能把整台主机停成离线，也不能计入人工失败；只有全部本地盘都低于安全空间时才使用 `storage_unavailable` 暂停主机上传。
- 默认保存位置按平台给：Windows 用系统盘，macOS / Linux 用个人影片目录（`~/Movies/PackingProofVideos`）。加载配置时清掉直接挂在只读系统卷根下的保存位置（旧版把 Windows 默认值在 macOS 上归一化出来的 `/快递打包视频` 就属于这类），改用默认位置；这类位置永远建不出来，留着会让保存主机每次启动都失败。
- 全部本地位置都不可用时的兜底位置与"添加磁盘"同一套规则：哪块盘就放哪块盘的 `PackingProofVideos` 目录（系统盘就是 `<系统盘>:\PackingProofVideos`），绝不允许落到程序安装目录下——`<程序目录>\Videos` 这类位置在升级、卸载、换安装目录时会把录像一起带走。旧版本已经按 `快递打包视频` 建好的目录不受影响，配置里记录的绝对路径继续有效。
- macOS 的外接盘固定挂在 `/Volumes/<盘>`：这一层不是挂载点（盘没接入）时按不可用 fail-closed，禁止在系统盘上建出同名目录继续写。`/` 是只读系统卷，保存位置不得直接落在它下面。
- Web 视频操作使用“剪辑”或“剪辑并下载”，不得称为“导出视频”，避免与原片下载混淆。

## 删除与文件替换安全

- 录像、数据库、配置、更新负载和生成输出的删除都按并发敏感操作处理。删除前必须在与创建或替换相同的同步范围内确认文件所有者、生命周期和源/目标关系。
- 回放里的单条“删除录像”（`Services/RecordingDeleteService.cs`）只删本机副本：记录置 `IsDeleted` 并写 `DeleteLogs`（原因码 `UserRequested`），备份位置上的归档副本按“程序只上传不删除”的既有约定保留，仍由容量清理与对账管理。判定统一走 `RecordingDeletePolicy`（界面与服务端共用）：录制中、归档传输中（`Copying`/`Verifying`）、`StorageState = Remote`（录像实体在录像主机上）以及本机找不到文件且没有完成归档证据的记录一律拒绝；**文件删不掉时绝不改数据库**，否则会留下“记录已删、文件永远留在磁盘上”的残留。删除在同一记录的所有权锁内进行，等待超时按“正在备份或清理”提示用户稍后再试。纯查看端不给删除入口。
- 用户删除的记录只保留一条归档副本（本地副本已删）：**它必须继续进 NAS 容量循环清理的候选**（`GetNasCleanupCandidates`、`NasCircularCleanupService` 按 `DeleteReasonCode = UserRequested` 单独放行），否则这条记录既不在界面上、也不会被任何流程回收，会永久占着备份盘。回收时只把归档状态改成 `NasDeleted` 并写删除日志，**不得覆盖用户删除的原因码**；对账发现归档已不存在时同样按“已回收”收尾，避免每轮重复探测。其它原因（容量清理、对账淘汰、备份丢失）删除的记录一律不因此进候选。
- 失败任务不能仅因目标存在就删除目标；目标可能由另一个并发任务成功发布，或源文件可能已被其他任务移动、替换。
- 不完整输出的清理必须位于其创建操作和锁内。只有原始源仍安全保留，且当前操作能证明目标由自己创建时，才允许删除。
- MKV 转 MP4 必须写入同目录临时文件，完成解码探测并刷到磁盘后再原子替换最终文件；只有替换成功后才能删除源 MKV。已存在的同名 MP4 也必须通过同样的探测与落盘检查，不能只凭“文件非空”就删除源文件。
- 自动删除重要数据时记录原因和精确目标；可行时优先使用可恢复清理或明确的数据库删除记录。
- 每项删除或替换修复都要增加竞态回归测试：任务 A 成功发布目标后，任务 B 才进入失败清理，测试必须证明 B 不会删除 A 的有效结果。

## 跨设备备份兼容性

- 设备注册、备份鉴权、上传和确认回执的变更都视为双端协议变更。主机和客户端必须显式交换协议、注册、鉴权、应用版本、构建版本和能力，不得只根据显示版本猜测兼容性。
- 电脑录像从机的常规心跳在已有配对凭据时必须使用签名鉴权；主机返回 401/403 时客户端必须进入“需要重新连接”状态并提示重新配对，不能继续显示在线，也不能等到第一次上传失败才发现。旧客户端未携带签名的兼容心跳仍可接受，但只能视为兼容路径
- 不兼容客户端必须在显示主机审批、签发/轮换/保存令牌之前被拒绝，并返回结构化升级信息：需要升级哪一端、最低兼容版本和可信下载地址。
- 手机或录制工位必须在请求令牌前拒绝不兼容主机。兼容失败可以阻断连接和备份，但绝不能删除或重置本地录像、数据库、上传队列、稳定设备 ID 或最近主机提示。
- 网络离线、超时、主机繁忙等可恢复上传失败必须持续退避重试，不能因为累计次数达到上限而永久停止。只有会话冲突、主机身份/版本/鉴权协议不兼容、无效确认、本地文件不存在等确定性原因才允许进入人工处理状态；升级后的自动恢复也必须只针对当前绑定保存主机，并清理旧的停止原因。
- 上传任务在主机过期或主机重启后返回 `upload_not_found` 时必须重新创建上传并从 0 继续。完整文件 SHA256 不一致时，客户端必须遵守主机返回的 `retryWholeFile` 与 `maxFileAttempts`：清空断点和缓存哈希，重新计算本地文件哈希并整文件重传；达到主机允许次数后才停止自动重试。
- 录制工位绑定保存主机后，所有已完成、仍在本机且尚未进入上传队列的 PC 录像都必须按正常上传策略入队，不能因为录像创建时间早于工位启用时间而永久漏传。上传仍逐条分片执行，沿用断点续传、主机校验、退避重试和缓存清理规则。
- 最低版本和协议号只放在集中兼容策略代码中，不在规范文档写死。调整策略或线协议时同步更新桌面端与移动端回归测试。
- 提高主机最低客户端版本前，先发布兼容客户端；发布前验证两个升级方向及更新但仍兼容的对端。

## 历史录像业务类型筛选

`GET /api/mobile-backup/videos` 新增可选 `mode=shipping|return`，省略或空值表示全部。非法值返回 HTTP 400 与 `invalid_recording_mode`。服务端在分页和统计前筛选，`total` 和 `deviceTotal` 使用同一业务类型及关键字条件；响应回显规范化的 `mode`。

手机在筛选请求中检查回显；旧电脑未回显时不把未筛选列表当成筛选结果，保留本地筛选并提示升级电脑端。该扩展不改变协议版本、鉴权或上传回执，不清理本地录像及设置。

## 心跳响应回传电脑名

`POST /api/connections/heartbeat` 的 200 响应新增 `computerName`，与注册响应的 `computerName` 同源（主机节点名，不是机器名）。手机端每次心跳后按它纠正"已连接电脑"显示名，主机改名后不必重新配对；字段缺失或为空时保留本地已存的名字，禁止用它清空。

该字段只影响展示名，不改变协议版本、鉴权、心跳间隔或"检查是否还是备份主机"的判定，旧客户端忽略即可。

## 设备身份与昵称

- 设备身份只有设备号（`VideoRecords.SourceDeviceId`）：筛选、列表、导出、归档目录一律按设备号命中；昵称只是显示属性，用户随时可以改
- 桌面端 NodeId 另有独立身份锚点：首次确定的有效 ID 写入 `identity\node-id.json`，配置丢失或回滚时以锚点恢复；Windows 连锚点也不存在时才用 MachineGuid 派生固定 ID。不得仅凭昵称、IP、最后在线时间自动合并设备，两台真实设备可能同名或共用地址；历史设备合并必须由用户明确确认同一物理设备，并保留审计记录，不能删除录像文件
- 设备录像目录名**就是完整设备号**（见 `Services/RecordingDeviceFolderNaming.cs`）。这条是硬约束：目录名必须是设备号的**纯函数**——同一个设备号永远同一个目录、不同设备号永远不同目录，不依赖任何需要持久化的分配状态
- 不要引入"主机分配的序号"之类更好看的方案。序号要靠一份额外的映射表存着，那份表丢失或损坏时所有设备都会重新编号，同一台设备的录像散进两个目录；分配、回收、落盘失败、以及昵称表自身的保留期与条数上限，每一处都是分裂风险。目录名难看由录像根目录下的快捷方式解决
- 也不要截短设备号。截短会撞号，撞上就是两台设备的录像混进同一个目录，比目录名难看严重得多。设备号含非法字符或超长而必须处理时，要补设备号哈希后缀，保证"不同设备号 → 不同目录"在任何输入下都成立
- 目录与昵称的对应关系由录像目录里的快捷方式给出（`Services/RecordingDeviceFolderShortcuts.cs`）：快捷方式建在分类目录里（`PhoneBackup\安卓1` -> `PhoneBackup\<设备号>`），只为磁盘上真实存在的设备目录建，改名后清掉旧链接。清理时只删确认指向本分类目录下设备目录的链接，用户自己放进来的文件一律不碰；外壳组件不可用（Windows 的 .lnk）或权限不足（macOS 的符号链接）时只记一次日志，绝不影响录像与备份。Windows 用 `.lnk`，macOS / Linux 用不带扩展名的目录符号链接（Finder 里是带箭头的替身），两者语义一致。早先的 `设备对照表.txt` 已由它取代并会被自动清掉

## 生成文件命名

新生成的录像、上传归档和导出文件一律使用 ASCII 命名，不把界面语言写进路径：

- 本地录像：`<单号>_<yyyyMMdd_HHmmss>_Ship.mkv` / `_Return.mkv`
- 手动开始且没有单号：`<yyyyMMdd_HHmmss>_Ship.mkv` / `_Return.mkv`
- 外部上传：`<根>\PhoneBackup|<PCUpload>\<设备号>\<yyyy-MM-dd>\<单号>_<时间>_Ship|Return.mp4`
- 导出单号：`Orders_<范围>_<时间>.xlsx`
- 桌面导出压缩版本：`<原文件名>_<AV1|H265|Source>_compressed.mp4`，默认保存到系统“视频”目录，不默认写回受管理的录像目录
- 桌面导出压缩版本在目标目录的隐藏临时工作目录内完成，确认源文件未变化且输出不超过目标大小后才原子发布；失败或取消只清理本次临时目录，不改原录像

旧版本已经生成的 `快递打包视频`、`手机备份`、`电脑上传` 目录和带中文模式后缀的文件保持原样，不迁移、不改名；读取与快捷方式扫描同时兼容新旧两种目录名。
- 录像目录树的递归扫描与目录遍历必须跳过符号链接与目录联接（`Services/RecordingTreeEnumeration.cs`）：macOS 在分类目录里放符号链接替身，默认枚举会把指向目录的链接当成普通子目录并跟着递归进去，同一份录像会被算两遍、清理与归档也会重复处理
- 两代老目录（`设备-<后六位>`、更早的 `<昵称>-<后六位>`）由 `Services/RecordingDeviceFolderMigrator.cs` 在启动时迁移，覆盖本地录像根与所有备份位置。约束：匹配方向是"从数据库的完整设备号算出后六位再去磁盘找"，两台设备后六位撞上时两边都跳过并告警（绝不猜归属）；只移动不复制不删除，目标已存在时按日期子目录合并且同名文件一律跳过；数据库回写带乐观条件，且只在文件确实已经在新位置时才改，不制造悬空路径
- 迁移必须可重复执行并自愈：搬完目录还没回写数据库就断电时，下一轮按"库里还是老路径、文件已在新位置"把数据库补上，因此不需要额外的迁移日志文件。NAS 不可达只跳过归档那一侧，本地照常迁移，下次启动再补；文件被占用同样是跳过而非失败
- 昵称只保存"最新一份映射"，不逐条写进录像记录：手机登记表 `mobile-backup-state\order-receivers.json`（设备号、昵称、平台、最后出现时间）与电脑昵称表 `computer-nicknames.json`。新写入的录像记录不再带昵称；历史记录里的 `SourceDeviceName` 是老库遗留值，只在主机完全不认识这台设备时兜底
- 设备只要在这台主机上留下过录像就长期保留，不按 30 天活跃期清理：映射是录像来源名的唯一来源，清掉它老录像就只剩设备号了。保留期只作用于"没有录像、也不是用户改名"的设备；条数上限 512，超限时先清这一类
- 主机启动时用库里已有的录像来源补齐映射（每台设备取最近一条记录里的名字，同名时最近还有录像的设备优先，另一台带上设备号后缀区分），老库升级后老录像即可显示同一个当前名字，设备不用等上线
- 命名只用"设备号 + 平台前缀"：平台未知（旧版 App 上报没带平台信息）时沿用这台设备已有的自动名前缀，不按"从机"兜底改名；没有设备号的匿名上报（未配对手机探测主机能力等）不登记设备，避免凭空多出"从机"
- 补齐时顺带修回被兜底命名改坏的名字：设备录像里用过"手机N/安卓N/苹果N/电脑N"而当前是"从机N"时改回那个名字，用户手改过的名字不动
- 上传落库用主机分配的昵称：电脑工位先经电脑昵称表分配，结果原样交给手机登记表（`trustProvidedName`），避免两张表各编一套"电脑N"；客户端自报的名字只在主机完全不认识这台设备时使用
- 昵称必须**跨两张表全局唯一**：只发心跳、没上传过录像的电脑工位不在手机登记表里，没上传过的手机也可能不在电脑昵称表里，所以两张表在查重名与自动编号时都要看对方。撞名的处理方式各自保留：工位名字由它自己上报（改名走心跳，没法交互拒绝）所以让开并加后缀，手机改名是显式接口调用所以直接拒绝、由用户换名
- 两张昵称表的读写失败都必须留痕：写失败记一次日志（昵称丢失会让录像来源名退回设备号、工位重新编号），读失败按空表继续但同样记日志，不得静默。落盘用"唯一命名的临时文件 + 原子替换"，写死 `.tmp` 会让崩溃残留与并发写互相踩；启动时清掉已退出进程留下的残留，跳过还活着的进程的
- 跨表查重名一律读对方的**不可变快照**，不得在自己的锁内回调对方查询：两张表各有一把锁，锁内互调时"一边改名、一边处理心跳"会 AB-BA 死锁。代价是极短的过期窗口，对人工低频的改名操作可以接受；每次改动条目后都要刷新自己的快照，否则对方查到旧名字
- 历史设备整理必须在主窗口与 Web 服务进入可用状态后于后台执行，禁止在启动路径同步扫描大库。后台最多每 12 小时做一次幂等对账，并持久化“上次成功检查时间”；刚检查过则下次启动顺延到到期时间，不重复扫库。周期对账只按当前登记的设备号做索引命中检查，不得反复对整个录像表做窗口聚合；全量昵称补齐只在维护状态版本升级时执行一次。整理只把“已无未删除录像”的设备解除长期保留位，并按现有保留期清掉非用户改名的陈旧登记；不能删除录像记录、归档或文件。用户主动“解绑”表示解除配对并撤销上传凭据，设备号与昵称继续作为历史墓碑保留，解绑设备号另存于 `mobile-backup-state\backup-device-removals.json`，不能只依赖可能被历史整理或旧版本清理的登记条目：它必须从从机列表、上传目标和本机/Web 回放设备筛选里消失，但旧录像、标签和按单号搜索不受影响；普通心跳不得恢复，只有重新扫码配对才清除墓碑。升级时还要把旧版已从登记中删除、但仍有有效录像的历史设备号一次性补入同一解绑状态；当前登记为空时不得执行这项迁移。历史墓碑昵称不占用当前昵称；昵称被新设备复用后，旧设备重新配对时必须自动获得新的唯一昵称
