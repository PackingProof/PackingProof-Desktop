# PackingProof 第三方扩展 API 路线图

## 目标

让 ERP、称重系统、电商平台油猴脚本和其他局域网适配器只负责读取其所属系统的数据，并通过统一协议与 PackingProof 协作。PackingProof 统一负责扫码事件、设备授权、订单合并、录像关联、播报、提示条幅、动态水印和错误处理，第三方不需要修改桌面端源码，也不需要重新实现 PackingProof 已有能力。

本路线图描述后续演进方向，不代表所有草案字段已经可用。当前已经发布的接口以 [EXTENSION_API_V1.md](EXTENSION_API_V1.md) 为准。

## 设计原则

1. **先复用现有能力**：开发新接口前先确认仓库是否已有对应服务、协议和测试
2. **发送事件，不广播隐私数据**：扫码任务只发送给已配对且声明对应能力的扩展，不向所有局域网设备裸广播
3. **语义数据优先**：第三方返回订单、重量、尺寸、退款状态等结构化数据，不能提交绘图、TTS、SQL、Shell 或 FFmpeg 指令
4. **录像立即开始，扩展异步补充**：外部系统超时或离线不能阻止录像启动，晚到的数据在会话有效期内合并
5. **未找到不等于失败**：必须区分明确未找到、超时、未授权、限流和服务不可用
6. **最小权限**：扩展令牌只允许用户批准的能力，不复用完整网页访问密钥或备份设备令牌
7. **兼容优先**：保留现有快递助手和旧订单接口，在通用协议稳定后逐步迁移
8. **服务端统一去重和合并**：第三方不需要各自重新实现订单缓存、来源优先级和重复播报控制

## 已有能力盘点

以下能力已经存在，后续应扩展或复用，禁止平行重写一套。

| 已有能力 | 当前实现 | 后续处理 |
| --- | --- | --- |
| 扩展能力查询 | `GET /api/extensions/v1/capabilities` | 扩充能力、协议和授权信息 |
| 第三方订单推送 | `POST /api/extensions/v1/orders` | 保留并增加幂等、结构化商品和结果明细 |
| 活跃录像查询 | `GET /api/extensions/v1/recordings/active` | 保留，用于兼容主动写入型设备 |
| 动态录像字段 | `POST /api/extensions/v1/recordings/{id}/data` | 保留，并允许通过扫码任务直接关联会话 |
| 快递助手查询任务 | `/api/order-lookup/pending`、`/api/order-lookup/result` | 从单领取者内部接口演进为多扩展任务协议 |
| 在线连接心跳 | `/api/connections/heartbeat`、`ConnectedClientRegistry` | 扩展客户端身份与能力声明复用此模型 |
| 订单接收设备发现 | `RecordingDeviceCatalog`、`MobileOrderReceiverRegistry` | 继续由主程序管理，第三方脚本不扫描局域网 |
| 订单缓存与录像快照 | `StoreOrderInfos`、数据库订单记录 | 由主程序统一处理来源合并和保存 |
| 订单播报与退款提醒 | `MainViewModel` 订单提示流程 | 第三方只返回语义数据，不能指定播放指令 |
| 设备审批授权 | 手机/电脑备份的 enrollment 与设备令牌 | 复用审批交互和安全模型，不复用其高权限令牌 |
| Web 访问保护 | `X-EPM-Access-Key` | 继续兼容人工或旧客户端，不作为扩展长期授权方案 |
| 用户脚本设备注入 | `PACKING_PROOF_RECORDERS`、`PACKING_PROOF_HOST` 等占位符 | 继续由安装向导维护，不让脚本自建设备管理 |

## 当前缺口

### 扩展专用注册与授权

当前扩展接口在网页保护开启时使用 Web 访问密钥，不适合作为长期的第三方扩展身份。需要新增扩展配对流程：

1. 扩展提交稳定实例 ID、名称、版本、来源和申请权限
2. PackingProof 显示批准窗口，明确列出该扩展希望读取或写入的能力
3. 用户允许后签发扩展专用令牌
4. 令牌绑定扩展实例和权限，可在设置中查看、撤销和重新授权
5. 令牌不能访问录像播放、删除、配置、备份和其他未授权接口

建议的权限粒度：

```text
orders.write
scan-tasks.read
scan-results.write
recordings.active.read
recording-fields.write
```

### 通用扫码任务

扫码后不应该要求称重系统先查询当前订单，也不应该让每个 ERP 修改 PackingProof 源码。PackingProof 应创建一次通用扫码任务，并只投递给已授权且声明相应能力的扩展。

任务草案：

```json
{
  "protocol": "packingproof-extension",
  "protocolVersion": 1,
  "taskId": "01J...",
  "eventType": "barcode.scanned",
  "trackingNumber": "YT123456",
  "recordingSessionId": "...",
  "recordingMode": "shipping",
  "occurredAt": "2026-08-23T08:30:00Z",
  "requestedCapabilities": [
    "order.lookup",
    "refund.lookup",
    "measurement.capture"
  ],
  "expiresAt": "2026-08-23T08:30:30Z"
}
```

约束：

- 只包含完成任务所需的最少信息
- `trackingNumber` 是本次扫描值，不包含数据库历史和其他客户数据
- `recordingSessionId` 用于把返回数据准确关联到本次录像
- 不支持对应能力的扩展不会收到任务
- 一个扫码任务可以被多个扩展分别响应
- 录像启动不等待所有扩展完成

### 多扩展响应

同一个扫码任务允许不同扩展返回不同类型的数据。

ERP 响应示例：

```json
{
  "taskId": "01J...",
  "providerId": "kuaimai.adapter",
  "resultId": "stable-result-id",
  "status": "found",
  "orders": [
    {
      "trackingNumber": "YT123456",
      "orderId": "ORDER-1",
      "buyerMessage": "请轻放",
      "sellerMemo": "核对颜色",
      "totalItemCount": 3,
      "products": [
        {
          "name": "蓝色水杯",
          "sku": "BLUE-500",
          "merchantSku": "PDD-001",
          "quantity": 3
        }
      ],
      "refundStatus": "none"
    }
  ],
  "observedAt": "2026-08-23T08:30:02Z"
}
```

称重系统响应示例：

```json
{
  "taskId": "01J...",
  "providerId": "scale.example",
  "resultId": "stable-result-id",
  "status": "completed",
  "recordingFields": {
    "weight": {
      "value": "1.25",
      "unit": "kg"
    },
    "length": {
      "value": "30",
      "unit": "cm"
    }
  },
  "observedAt": "2026-08-23T08:30:04Z"
}
```

称重系统不需要再次查询“当前是什么订单”。它只需响应收到的 `taskId`，PackingProof 根据任务中已经绑定的 `recordingSessionId` 和快递单号完成关联。为兼容连续称重，允许同一扩展在任务有效期内更新结果，以最后一个有效且时间更新的读数为准。

### 结果状态

订单或退款查询至少区分：

| 状态 | 含义 | PackingProof 行为 |
| --- | --- | --- |
| `found` | 明确查询到数据 | 合并订单并更新提示、播报和录像快照 |
| `not_found` | 上游明确确认不存在 | 可按用户设置提示“单号不在系统中” |
| `completed` | 非订单任务正常完成 | 保存称重、尺寸等扩展字段 |
| `unavailable` | 上游服务不可用 | 显示连接异常，不得当作未找到 |
| `unauthorized` | ERP 或平台凭据失效 | 提示扩展重新授权 |
| `rate_limited` | 上游限流 | 延迟重试，不得重复报警 |
| `timeout` | 查询超时 | 录像继续，结果记为未确认 |
| `invalid_request` | 扩展无法处理任务 | 记录诊断，不污染订单数据 |

### 超时和迟到结果

- 每个任务包含 `expiresAt`
- 主界面等待提示使用较短软超时，例如 3 至 8 秒
- 任务生命周期使用较长硬超时，例如 30 秒
- 软超时后录像照常进行，不能播报“订单不存在”
- 硬超时后拒绝改变已结束任务的订单判断
- 对仍处于录制中的会话，可允许经规则验证的迟到水印字段写入
- 录像结束后保留已有字段，但不允许继续改写录像画面

具体时间必须在实现阶段集中配置并通过测试确定，不能散落在脚本中。

### 幂等和来源合并

每次响应携带稳定的 `resultId`。主机以扩展身份、`providerId` 和 `resultId` 去重，重复提交返回成功但不重复播报。

订单合并必须由 PackingProof 统一执行：

- 空值不得覆盖已有非空值
- 明确退款不得被普通页面的旧数据清除
- 新鲜的权威查询可以替换过期缓存
- `not_found` 不能删除其他来源已经确认的订单
- 每个字段记录来源和观察时间，避免不同 ERP 相互覆盖
- 现有 `OrderInfo`、订单缓存和退款保护逻辑优先复用

### 结构化商品

保留现有 `productInfo` 兼容字段，同时增加结构化 `products`。PackingProof 根据 `quantity` 统一计算或校验 `totalItemCount`，用于商品件数播报和右下角多件数字提示。

第一阶段不开放远程商品图片。图片会引入身份 Cookie、外部追踪、缓存、恶意文件和录像性能问题，待结构化商品协议稳定后另行评估。

### 受控用户提示

第三方不能提交任意 TTS 指令、音频路径或播放参数。扩展只返回状态和结构化数据，PackingProof 使用本地化文案和用户设置决定是否：

- 显示买家留言或卖家备注
- 播报商品总件数
- 显示右下角多件数字
- 发出退款警报
- 提示订单明确不存在
- 提示扩展离线或凭据失效

## 与现有订单查询接口的关系

现有 `/api/order-lookup/pending` 和 `/api/order-lookup/result` 已实现长轮询、任务 ID、超时和结果回传，当前主要服务于快递助手退款核验。它不能直接作为最终通用协议，原因是：

- 一个任务目前只允许一个领取者
- 结果只有成功或失败，无法区分未找到、超时、未授权和限流
- 没有扩展身份、权限和来源元数据
- 任务只携带快递单号，没有录像会话和请求能力
- 主要围绕订单快照设计，不能表达称重等独立响应

后续应复用其任务存储、长轮询信号、超时清理和现有退款测试，逐步迁移到扩展任务协议，而不是另写一套并立即删除旧接口。

## 兼容边界

- `/api/extensions/v1/*` 是当前对第三方公开的稳定接口；同一 v1 内只允许增加可忽略的响应字段和可选请求字段
- 已发布字段的名称、类型、含义、状态码和限制不能在 v1 内静默改变
- 客户端必须忽略不认识的响应字段，主机对可选的未知请求字段保持兼容
- 需要改变既有字段语义或安全模型时，必须通过能力声明和新的协议版本协商
- `/api/orderinfo`、`/api/orderinfo/broadcast` 是历史兼容接口，不作为新第三方开发入口
- `/api/order-lookup/pending`、`/api/order-lookup/result` 当前属于快递助手兼容接口；通用扫码任务上线后仍保留至少一个正式发布周期，并在官方脚本完成双协议兼容及迁移验证后再决定停用时间
- Web 访问密钥鉴权在扩展专用令牌发布前继续有效；新令牌上线不能让现有 v1 客户端立即失效
- 固定契约夹具位于 `ExpressPackingMonitoring.Tests/Fixtures/ExtensionApiV1`，相关 HTTP 集成测试是修改 v1 服务端行为前必须通过的兼容门禁

## 验收标准

统一扩展协议达到以下条件后，第三方才不需要修改 PackingProof 核心源码：

1. 扫码后，多个已授权扩展可以同时收到同一个任务
2. 称重系统无需自行查询当前订单即可把读数关联到本次录像
3. ERP 可以明确返回命中、未找到、超时、未授权和不可用
4. 一个扩展离线或超时不阻塞录像，也不影响其他扩展
5. 重复响应不会重复播报或污染数据库
6. 第三方无法访问未获授权的录像、配置、备份和删除接口
7. 快递助手现有订单联动和退款核验继续通过原有测试
8. 拼多多和快麦原型只实现平台适配，不重复实现设备管理、播报、水印和录像逻辑

## 暂不纳入范围

- 在 PackingProof 进程内加载第三方 DLL 或执行第三方代码
- 第三方自定义 SQL、Shell、PowerShell、FFmpeg、绘图或 TTS 指令
- 向所有局域网设备无鉴权广播扫码数据
- 直接把完整 Web 访问密钥或备份设备令牌签发给油猴脚本
- 远程商品图片下载和烧录
- 将某个 ERP 的 AppKey、AppSecret 或 Token 保存在 PackingProof 通用配置中
