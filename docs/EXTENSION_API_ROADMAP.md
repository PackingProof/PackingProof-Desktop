# PackingProof 第三方扩展 API 路线图

## 目标

让 ERP、称重系统、电商平台油猴脚本和其他局域网适配器只负责读取其所属系统的数据，并通过统一协议与 PackingProof 协作。PackingProof 统一负责扫码事件、设备授权、订单合并、录像关联、播报、提示条幅、动态水印和错误处理，第三方不需要修改桌面端源码，也不需要重新实现 PackingProof 已有能力。

本路线图描述后续演进方向，不代表所有草案字段已经可用。当前已经发布的接口以 [EXTENSION_API_V1.md](EXTENSION_API_V1.md) 为准。

## 设计原则

1. **先复用现有能力**：开发新接口前先确认仓库是否已有对应服务、协议和测试
2. **发送事件，不广播隐私数据**：扫码任务只发送给已配对且声明对应能力的扩展，不向所有局域网设备裸广播
3. **语义数据优先**：第三方返回订单、重量、尺寸、退款状态等结构化数据，不能提交绘图、TTS、SQL、Shell 或 FFmpeg 指令
4. **录像立即开始，扩展异步补充**：外部系统超时或离线不能阻止录像启动，晚到的数据在会话有效期内合并
5. **未找到不等于失败**：必须区分明确未找到、超时、未授权、限流和服务不可用
6. **最小权限**：扩展令牌只允许用户批准的能力，不复用完整网页访问密钥或备份设备令牌
7. **兼容优先**：保留现有快递助手和旧订单接口，在通用协议稳定后逐步迁移
8. **服务端统一去重和合并**：第三方不需要各自重新实现订单缓存、来源优先级和重复播报控制

## 架构角色与拓扑

统一协议必须区分以下角色，不能把它们都叫作“设备”：

| 角色 | 职责 |
| --- | --- |
| 录像节点 | 实际扫码、录像并拥有录像会话，可以是电脑或手机 |
| 扩展协调主机 | 保存扩展身份、授权和任务投递状态，通常是当前桌面主机；单机电脑版可以同时是录像节点 |
| 扩展适配器 | 对接 ERP、称重仪或电商网页，只处理获授权且路由到自己的任务 |
| 保存主机 | 保存上传录像；可以与扩展协调主机是同一台电脑，但不是协议上的同一角色 |

任务不能只携带 `recordingSessionId`，必须使用：

```text
originNodeId + recordingSessionId + taskId
```

原因是手机和多台电脑可能同时录像，而录像会话只在来源节点内具备业务上下文。扩展协调主机负责把响应路由回来源节点；如果来源节点就是本机，则直接应用。

首期实现范围固定为“桌面录像节点与扩展协调主机位于同一进程”。跨手机和多电脑转发必须先定义双端能力协商、离线行为和兼容版本，不能从桌面单机实现中隐式推断。

## 架构评审结论

### 扫码事件、投递和响应必须分离

一次有效订单扫码创建一个不可变的 `ScanEvent`。协调主机根据已授权扩展的能力和工位绑定，为每个“扩展实例 + 能力”生成独立 `Delivery`。扩展提交一个或多个 `Result`。

```text
ScanEvent（只创建一次）
  ├─ Delivery：快麦 ERP 适配器 / order.lookup
  │    └─ Result：订单信息
  ├─ Delivery：快麦 ERP 适配器 / refund.lookup
  │    └─ Result：退款状态
  ├─ Delivery：当前工位称重适配器 / measurement.capture
  │    ├─ Result revision 1：正在稳定
  │    └─ Result revision 2：稳定重量
  └─ Delivery：尺寸测量适配器 / measurement.capture
       └─ Result：长宽高
```

每条投递只对应一种能力。不能让一条投递同时承载订单、退款和测量结果，否则其中一个能力先返回最终状态后，会错误关闭其他仍在处理的能力。扩展可以连续领取多条投递，但每条投递分别确认、修订和完成。

不能沿用当前 `PendingOrderLookup.Claimed` 的单次抢占模型。否则第一个轮询者会拿走任务，其他扩展永远看不到；简单移除 `Claimed` 又会导致同一扩展无限重复领取。每个投递至少记录：

- `deliveryId`
- `taskId`
- 目标扩展实例 ID
- 投递状态与尝试次数
- 首次投递、最近投递和过期时间
- 已确认的最新响应修订号
- 对应的单一 capability

传输采用带超时的 HTTP 长轮询和至少一次投递。重复领取是正常情况，服务端通过 `deliveryId + revision` 保证传输幂等，不要求油猴脚本保持永久在线，也不在第一阶段引入 WebSocket。

传输幂等与业务幂等必须分开：

- `deliveryId + revision` 防止同一投递的网络重试重复推进状态
- `extension identity + providerId + resultId` 防止重装、重连和主机重启后的同一业务结果重复写库或重复播报
- 活跃任务可以在进程重启后直接过期，但已经接收的业务结果和幂等记录必须持久化

响应不能先在内存中标记为已接受、再尝试写入业务数据。服务端必须先把规范化结果写入持久化 Result Inbox，并在同一事务中记录已接收 revision；后续订单合并、水印字段写入和播报由可重试的结果应用器处理。这样即使进程在接受响应后退出，也不会出现“扩展重试得到重复响应，但订单或重量从未写入”的数据丢失。

### 扩展路由不能等同于局域网广播

扩展授权时必须选择路由范围：

- ERP、电商平台适配器可以授权为“所有录像工位”
- 称重仪、尺寸仪等物理设备默认只能绑定一个或明确选择的录像工位
- 未绑定工位的物理设备不接收扫码任务
- 扩展不能通过响应修改任务中的来源节点、会话 ID 或快递单号

这样可以避免两张打包台同时工作时，A 工位的重量被写入 B 工位录像。

### 授权是公开任务接口的前置条件

可以先在内部实现和测试任务代理，但不得先发布依赖 Web 密钥的通用任务接口，再在后续版本改成扩展令牌。公开接口必须从第一版起使用扩展身份和最小权限令牌，否则客户端会依赖临时鉴权方式并产生二次迁移。

脚本导入、脚本安装和扩展授权是三个不同动作：

- 导入只保存并检查 `.user.js`
- 安装只把脚本交给 Tampermonkey
- 授权由运行中的脚本实例发起，用户确认后签发令牌

导入成功不能被视为脚本可信，也不能自动获得订单或录像数据权限。

扩展令牌使用独立的扩展根密钥签发，不能与 Web 密钥、备份设备根密钥或设备令牌互相派生。请求鉴权复用现有签名协议的安全思想，但使用独立的协议名称、请求头和密钥域：

- 请求包含扩展实例 ID、协议版本、时间戳、nonce、请求体摘要和签名
- 主机校验时钟窗口和 nonce，拒绝重放请求
- 主机持久化的是扩展授权、权限和可验证凭据，不在日志输出原始令牌
- 权限增加、提供方身份变化或物理工位绑定变化必须重新批准
- 仅更新显示名称或兼容版本不自动扩大权限
- 设置页允许查看最近在线时间、已批准权限、绑定工位并撤销授权

油猴脚本可以把自己的扩展令牌保存在脚本管理器隔离存储中，但任何在该脚本上下文执行的更新代码都可能使用这个令牌。PackingProof 无法把第三方脚本更新自动变成可信代码，因此批准窗口和文档必须明确显示脚本来源；第三方脚本的后续更新安全由其发布者和用户共同负责。官方脚本身份与第三方脚本身份不能混用。

扩展 enrollment 接口本身不持有令牌，必须按来源地址和实例 ID 限流。只有用户当前可见的审批请求才能签发凭据，后台脚本不能通过重复请求制造无限弹窗。

HTTP 请求中的 `extensionInstanceId` 只能作为一致性检查，不能作为可信身份。签名验证层必须从扩展凭据构造 `AuthenticatedExtensionContext`，其中包含实例 ID、已批准权限、工位绑定、凭据代次和协议版本；路由与 Broker 只接收这个可信上下文。请求体声明的实例、权限或工位不得扩大令牌已经批准的范围。

### 扫码事件必须在录像会话建立后发布

当前桌面流程在 `InternalStartRecordingAsync` 中创建录像会话并写入数据库。因此扩展扫码事件必须在该方法成功返回、`recordingSessionId` 和记录 ID 都可用之后发布。

- 录像启动失败时不得发布可写水印的任务
- 连续扫码先结束上一会话，再为新会话发布新任务
- 条码冷却、商品码、命令码和非法单号不得创建扩展任务
- 任务响应只绑定创建时的不可变会话，不能读取“当前会话”进行猜测

### 称重是采集过程，不是订单查询

扫码事件用于通知称重适配器开始或确认一次采集，但称重结果可能需要等待秤稳定。测量响应除数值和单位外还需要：

```json
{
  "measurementType": "weight",
  "value": "1.25",
  "unit": "kg",
  "stable": true,
  "capturedAt": "2026-08-23T08:30:04Z",
  "revision": 2
}
```

约束：

- `stable=false` 的中间读数默认不写入最终录像字段
- 同一投递只接受递增修订号，乱序旧读数不能覆盖新读数
- 单位由协议白名单规范化，不能把带指令的自由文本当数值
- 去皮、负重量、超量程和设备错误使用结构化状态表达
- 任务软超时后允许稳定读数在硬过期前到达，但不能串到下一单

### 查询结论按提供方独立保存

一个 ERP 返回 `not_found` 只代表该提供方没有找到，不能清除另一个来源已经确认的订单。协调主机先保存每个提供方的原始结论，再运行确定性的字段合并策略。

- 只有明确 `found` 的数据参与订单字段合并
- `not_found` 仅在所有被要求的权威订单提供方都明确返回后，才可以形成全局“未找到”提示
- `timeout`、`unavailable`、`provider_auth_required` 和 `rate_limited` 永远不能转成 `not_found`
- 退款状态必须保留来源和观察时间，沿用现有“普通旧数据不清除明确退款”的保护规则

### 任务不应阻塞录像主路径

任务创建、持久化和通知不得占用录像锁或帧处理线程。创建失败只记录诊断并提示扩展不可用，不能回滚已成功启动的录像。

任务本身是短期协调状态，可以在进程重启后过期；扩展授权、Result Inbox、业务幂等记录以及已经接受的订单快照和录像字段必须持久化。实现必须设置：

- 每扩展最大未完成投递数
- 主机全局最大活动任务数
- 单次响应体和字段数量限制
- 轮询频率和按扩展身份限流
- 清理任务时不删除已经写入的订单或录像字段

活跃投递、诊断快照和业务幂等记录使用不同保留期，不能随着短期任务一起删除。Result Inbox 只有在结果成功应用且超过幂等保留期后才能清理。

### 隐私、日志和保留期限

- 扫码任务、订单内容、重量和客户备注不得写入普通信息级日志全文
- 诊断日志仅记录脱敏后的任务 ID、扩展 ID、状态、耗时和字段数量
- AppSecret、Session、刷新令牌和扩展令牌不得进入 PackingProof 通用配置或反馈包
- 扩展授权和任务协调状态存放在 `mobile-backup-state` 的独立子目录；短期投递可以清理，已经接受的业务数据继续存入现有数据库
- 扩展只能读取路由给自己的任务，不能列举其他扩展、其他工位或历史任务

## 已有能力盘点

以下能力已经存在，后续应扩展或复用，禁止平行重写一套。

| 已有能力 | 当前实现 | 后续处理 |
| --- | --- | --- |
| 扩展能力查询 | `GET /api/extensions/v1/capabilities` | 扩充能力、协议和授权信息 |
| 第三方订单推送 | `POST /api/extensions/v1/orders` | 保留并增加幂等、结构化商品和结果明细 |
| 活跃录像查询 | `GET /api/extensions/v1/recordings/active` | 保留，用于兼容主动写入型设备 |
| 动态录像字段 | `POST /api/extensions/v1/recordings/{id}/data` | 保留，并允许通过扫码任务直接关联会话 |
| 快递助手查询任务 | `/api/order-lookup/pending`、`/api/order-lookup/result` | 从单领取者内部接口演进为多扩展任务协议 |
| 在线连接心跳 | `/api/connections/heartbeat`、`ConnectedClientRegistry` | 扩展客户端身份与能力声明复用此模型 |
| 订单接收设备发现 | `RecordingDeviceCatalog`、`MobileOrderReceiverRegistry` | 继续由主程序管理，第三方脚本不扫描局域网 |
| 订单缓存与录像快照 | `StoreOrderInfos`、数据库订单记录 | 由主程序统一处理来源合并和保存 |
| 订单播报与退款提醒 | `MainViewModel` 订单提示流程 | 第三方只返回语义数据，不能指定播放指令 |
| 设备审批授权 | 手机/电脑备份的 enrollment 与设备令牌 | 复用审批交互和安全模型，不复用其高权限令牌 |
| Web 访问保护 | `X-EPM-Access-Key` | 继续兼容人工或旧客户端，不作为扩展长期授权方案 |
| 用户脚本设备注入 | `PACKING_PROOF_RECORDERS`、`PACKING_PROOF_HOST` 等占位符 | 继续由安装向导维护，不让脚本自建设备管理 |

## 当前缺口

### 扩展专用注册与授权

当前扩展接口在网页保护开启时使用 Web 访问密钥，不适合作为长期的第三方扩展身份。需要新增扩展配对流程：

1. 扩展提交稳定实例 ID、名称、版本、来源和申请权限
2. PackingProof 显示批准窗口，明确列出该扩展希望读取或写入的能力
3. 用户允许后签发扩展专用令牌
4. 令牌绑定扩展实例和权限，可在设置中查看、撤销和重新授权
5. 令牌不能访问录像播放、删除、配置、备份和其他未授权接口

建议的权限粒度：

```text
orders.write
scan-tasks.read
scan-results.write
recordings.active.read
recording-fields.write
```

### 通用扫码任务

扫码后不应该要求称重系统先查询当前订单，也不应该让每个 ERP 修改 PackingProof 源码。PackingProof 应创建一次通用扫码任务，并只投递给已授权且声明相应能力的扩展。

任务草案：

```json
{
  "protocol": "packingproof-extension",
  "protocolVersion": 1,
  "taskId": "01J...",
  "eventType": "barcode.scanned",
  "trackingNumber": "YT123456",
  "originNodeId": "recording-node-001",
  "recordingSessionId": "...",
  "recordingMode": "shipping",
  "occurredAt": "2026-08-23T08:30:00Z",
  "requestedCapabilities": [
    "order.lookup",
    "refund.lookup",
    "measurement.capture"
  ],
  "expiresAt": "2026-08-23T08:30:30Z"
}
```

约束：

- 只包含完成任务所需的最少信息
- `trackingNumber` 是本次扫描值，不包含数据库历史和其他客户数据
- `recordingSessionId` 用于把返回数据准确关联到本次录像
- 不支持对应能力的扩展不会收到任务
- 一个扫码任务可以被多个扩展分别响应
- 录像启动不等待所有扩展完成

### 多扩展响应

同一个扫码任务允许不同扩展返回不同类型的数据。

ERP 响应示例：

```json
{
  "taskId": "01J...",
  "providerId": "kuaimai.adapter",
  "resultId": "stable-result-id",
  "status": "found",
  "orders": [
    {
      "trackingNumber": "YT123456",
      "orderId": "ORDER-1",
      "buyerMessage": "请轻放",
      "sellerMemo": "核对颜色",
      "totalItemCount": 3,
      "products": [
        {
          "name": "蓝色水杯",
          "sku": "BLUE-500",
          "merchantSku": "PDD-001",
          "quantity": 3
        }
      ],
      "refundStatus": "none"
    }
  ],
  "observedAt": "2026-08-23T08:30:02Z"
}
```

称重系统响应示例：

```json
{
  "taskId": "01J...",
  "providerId": "scale.example",
  "resultId": "stable-result-id",
  "status": "completed",
  "recordingFields": {
    "weight": {
      "value": "1.25",
      "unit": "kg"
    },
    "length": {
      "value": "30",
      "unit": "cm"
    }
  },
  "observedAt": "2026-08-23T08:30:04Z"
}
```

称重系统不需要再次查询“当前是什么订单”。它只需响应分配给自己的 `deliveryId` 和 `taskId`，PackingProof 根据任务中已经绑定的来源节点、录像会话和快递单号完成关联。为兼容连续称重，允许同一扩展在任务有效期内使用递增 `revision` 更新结果，仅接受通过校验的最新稳定读数。

### 结果状态

订单或退款查询至少区分：

| 状态 | 含义 | PackingProof 行为 |
| --- | --- | --- |
| `found` | 明确查询到数据 | 合并订单并更新提示、播报和录像快照 |
| `not_found` | 上游明确确认不存在 | 可按用户设置提示“单号不在系统中” |
| `completed` | 非订单任务正常完成 | 保存称重、尺寸等扩展字段 |
| `unavailable` | 上游服务不可用 | 显示连接异常，不得当作未找到 |
| `provider_auth_required` | ERP 或平台凭据失效 | 提示扩展重新授权上游平台；PackingProof 扩展令牌失败仍使用 HTTP 401/403 |
| `rate_limited` | 上游限流 | 延迟重试，不得重复报警 |
| `timeout` | 查询超时 | 录像继续，结果记为未确认 |
| `invalid_request` | 扩展无法处理任务 | 记录诊断，不污染订单数据 |

### 超时和迟到结果

- 每个任务包含 `expiresAt`
- 主界面等待提示使用较短软超时，例如 3 至 8 秒
- 任务生命周期使用较长硬超时，例如 30 秒
- 软超时后录像照常进行，不能播报“订单不存在”
- 硬超时后拒绝改变已结束任务的订单判断
- 对仍处于录制中的会话，可允许经规则验证的迟到水印字段写入
- 录像结束后保留已有字段，但不允许继续改写录像画面

具体时间必须在实现阶段集中配置并通过测试确定，不能散落在脚本中。

### 幂等和来源合并

每次响应携带稳定的 `resultId`。主机以扩展身份、`providerId` 和 `resultId` 去重，重复提交返回成功但不重复播报。

订单合并必须由 PackingProof 统一执行：

- 空值不得覆盖已有非空值
- 明确退款不得被普通页面的旧数据清除
- 新鲜的权威查询可以替换过期缓存
- `not_found` 不能删除其他来源已经确认的订单
- 每个字段记录来源和观察时间，避免不同 ERP 相互覆盖
- 现有 `OrderInfo`、订单缓存和退款保护逻辑优先复用

### 结构化商品

保留现有 `productInfo` 兼容字段，同时增加结构化 `products`。PackingProof 根据 `quantity` 统一计算或校验 `totalItemCount`，用于商品件数播报和右下角多件数字提示。

第一阶段不开放远程商品图片。图片会引入身份 Cookie、外部追踪、缓存、恶意文件和录像性能问题，待结构化商品协议稳定后另行评估。

### 受控用户提示

第三方不能提交任意 TTS 指令、音频路径或播放参数。扩展只返回状态和结构化数据，PackingProof 使用本地化文案和用户设置决定是否：

- 显示买家留言或卖家备注
- 播报商品总件数
- 显示右下角多件数字
- 发出退款警报
- 提示订单明确不存在
- 提示扩展离线或凭据失效

### 扩展数据与水印显示必须解耦

重量、尺寸等第三方字段首先是结构化录像元数据，水印只是其中一种展示方式。协议不能把“接收数据”和“烧录水印”设计成同一个不可分割动作。

- `recording-fields.write` 权限决定扩展能否提交并持久化字段
- “显示第三方水印”设置决定字段是否进入预览和录像画面
- 关闭显示不能伪装成接口写入成功后悄悄丢弃数据
- 撤销扩展权限后必须拒绝新的字段写入
- 已经烧录的视频帧无法回写或撤销，设置文案必须明确这一点

当前配置名 `EnableThirdPartyWatermark` 实际只控制渲染，接口仍会保存字段。实现授权管理时应把用户可见文案调整为“显示第三方水印”，避免用户误以为关闭后主机不再接收或保存第三方数据。

## 与现有订单查询接口的关系

现有 `/api/order-lookup/pending` 和 `/api/order-lookup/result` 已实现长轮询、任务 ID、超时和结果回传，当前主要服务于快递助手退款核验。它不能直接作为最终通用协议，原因是：

- 一个任务目前只允许一个领取者
- 结果只有成功或失败，无法区分未找到、超时、未授权和限流
- 没有扩展身份、权限和来源元数据
- 任务只携带快递单号，没有录像会话和请求能力
- 主要围绕订单快照设计，不能表达称重等独立响应

后续应复用其任务存储、长轮询信号、超时清理和现有退款测试，逐步迁移到扩展任务协议，而不是另写一套并立即删除旧接口。

## 兼容边界

- `/api/extensions/v1/*` 是当前对第三方公开的稳定接口；同一 v1 内只允许增加可忽略的响应字段和可选请求字段
- 已发布字段的名称、类型、含义、状态码和限制不能在 v1 内静默改变
- 客户端必须忽略不认识的响应字段，主机对可选的未知请求字段保持兼容
- 需要改变既有字段语义或安全模型时，必须通过能力声明和新的协议版本协商
- `/api/orderinfo`、`/api/orderinfo/broadcast` 是历史兼容接口，不作为新第三方开发入口
- `/api/order-lookup/pending`、`/api/order-lookup/result` 当前属于快递助手兼容接口；通用扫码任务上线后仍保留至少一个正式发布周期，并在官方脚本完成双协议兼容及迁移验证后再决定停用时间
- Web 访问密钥鉴权在扩展专用令牌发布前继续有效；新令牌上线不能让现有 v1 客户端立即失效
- 固定契约夹具位于 `ExpressPackingMonitoring.Tests/Fixtures/ExtensionApiV1`，相关 HTTP 集成测试是修改 v1 服务端行为前必须通过的兼容门禁

## 验收标准

统一扩展协议达到以下条件后，第三方才不需要修改 PackingProof 核心源码：

1. 扫码后，多个已授权扩展可以同时收到同一个任务
2. 称重系统无需自行查询当前订单即可把读数关联到本次录像
3. ERP 可以明确返回命中、未找到、超时、未授权和不可用
4. 一个扩展离线或超时不阻塞录像，也不影响其他扩展
5. 重复响应不会重复播报或污染数据库
6. 第三方无法访问未获授权的录像、配置、备份和删除接口
7. 快递助手现有订单联动和退款核验继续通过原有测试
8. 拼多多和快麦原型只实现平台适配，不重复实现设备管理、播报、水印和录像逻辑
9. 多工位并发扫码时，物理测量设备不会把结果写入其他工位
10. 连续扫码、重复投递和乱序测量响应不会污染上一单或下一单

## 暂不纳入范围

- 在 PackingProof 进程内加载第三方 DLL 或执行第三方代码
- 第三方自定义 SQL、Shell、PowerShell、FFmpeg、绘图或 TTS 指令
- 向所有局域网设备无鉴权广播扫码数据
- 直接把完整 Web 访问密钥或备份设备令牌签发给油猴脚本
- 远程商品图片下载和烧录
- 将某个 ERP 的 AppKey、AppSecret 或 Token 保存在 PackingProof 通用配置中
